## kaizen
Kaizen is the lean habit of improving a process in small steps. Here is how I apply it. When a sequence of steps works, I write it down and make it the standard procedure for every work item. That is stage 7. When the same mistake happens a second time, I add a rule to that procedure. On the slide each red dot is an incident, and each one lifts the line a step.

The order matters. Ohno put it as "There can be no kaizen without a standard", quoted by the Lean Enterprise Institute. If the procedure lives only in someone's head, there is nowhere to add the rule, and the next agent session repeats the mistake. So run a few items by hand, pick the cleanest complete run and write that down. Then let each incident refine it. Lean calls this standard work, and the rule you add is what a blameless postmortem produces. Rules can also go. At each review, a rule that has not fired or caught anything in an agreed period gets removed or simplified. The [default period](../../docs/06-adoption-and-measurement.md#removing-process) is four to six weeks of active work.

## merged
Every work item moves through fixed statuses: proposed, ready, in-progress, in-review, merged, done. People mix up the last two. Merged means the change is in the code. Done means someone checked it where it runs, with evidence that each acceptance criterion holds in the target environment. A change that was merged but never deployed is not done.

Blocked is the only detour, and it has to say something. A blocked item records what blocks it and since when. Once the blocker is gone, it returns to the status it had before. Done and dropped are final, so reopening means a new item that links to the old one. The [status transitions](../../docs/05-work-item-procedure.md#status-transitions) page has the full table.

Stage 8, status verification, exists to catch an item reported as done when it was only merged. The repo ships a reference script, `tools/verify_status.py`, that checks a backlog against these rules and rejects a done row without an evidence link. A Definition of Done is a team's agreed test for when work counts as finished. This script checks it for you, so nobody has to remember.

## evidence
An agent will tell you a change "should work". That is not evidence. A green pipeline on its own is not evidence either. If a run goes green on a retry with no code change, that tells you the test is flaky. A cancelled or skipped run proves nothing. When a system reports its own success, look at the target system yourself. Evidence is the check that ran on the final commit, plus its output, kept. Anthropic's own advice is to ask the agent for exactly that: "evidence: the command it ran and its output".

I split evidence into two kinds. Computational evidence is a command whose output proves the criterion. Inferential evidence covers what a computer cannot judge, such as usability or value, so a named human approves it. An agent can gather and summarise the material, but it cannot be the judge. When you write acceptance criteria, first try to turn each one into a count or a measurement. Only when that fails, label it `inferential` and name the judge. The [evidence rules](../../docs/05-work-item-procedure.md#evidence-quality) follow evidence-based auditing as in ISO 19011.

## risk
A gate is a point where a human must approve before work moves on. Giving every change the same gates is too heavy for scaffolding and too light for payments or personal data. So each item gets a risk tier, and the tier sets how many gates it passes. Local means reversible and yours. It touches only the item's own workspace and passes one gate, the change gate before merge. Shared means others depend on it, so it also needs a plan gate before work starts. Irreversible means production, money or personal data. It adds a release gate, where a second human who is neither the owner nor the author approves.

To classify an item, ask the irreversible question first, then the shared one. The first yes sets the tier, and the riskiest step sets it for the whole item. When unsure, go up one tier. An approval must be dated before the action it approves, or it is just paperwork after the fact. I wrote the [risk tiers](../../docs/05-work-item-procedure.md#risk-tiers) after the method was bootstrapped on one real project, so they are an untested proposal.

## review
Stage 3 covers roles and separation of duties. Every area gets one owner who writes the change and a reviewer who is someone else. The reviewer gets the change and the acceptance criteria, but never the author's reasoning, meaning the plan or the conversation that produced it. A reviewer who has read the author's plan tends to agree with it. Anthropic's guidance is to use a reviewer that "never saw your conversation". Reviewer agents also get read-only access.

Authors never approve their own work. An agent reviewer can add findings, but it does not count as the human approval. In a team this maps onto tools you already have. The pull request approval is the change gate. Code owner rules decide who approves which paths, and branch protection blocks a merge without that approval. The older names are separation of duties, maker-checker (one person makes, another checks) or the four-eyes principle, and code owners. You need [stage 3](../../docs/03-method.md#stage-3-roles-and-separation-of-duties) when two agents change the same thing, or when whoever did the work also reviews it. Start with one owner and one reviewer.

## sentence
Before you copy any template, write one sentence: the failure you keep seeing, and where you saw it. The quick start gives an example: "every agent session starts from zero and I explain the same setup each time". I call that sentence a trigger, because it tells you which stage to add. This one points to stage 2, the context file, which gives every agent and person the same starting point. Write the sentence in your decision log, next to the stage it calls for. If you cannot write it, you probably do not need the method yet.

Copy only the files for the stages you use. Copying the whole templates folder works, but you get files for stages no failure has asked for. The [quick start](../../docs/01-quick-start.md#before-you-start) walks through the first files one at a time.

Some work is too small for any of this. A change you can make, check and undo in under an hour skips it. Keep one habit even then: do not call it done until you have seen it work.

## maturity
Each stage exists to fix one specific failure, so you only need the stages whose failure you have. The levels group stages that usually arrive together. Level 0, ad hoc, has no stages and fits when you explore an idea alone. Move to level 1, briefed, once more than one session, agent or person is involved. It adds stages 0, 1 and 2: the AI stance, the situation analysis and the context file. Level 2, planned, adds stages 4 and 5, the phased plan and the backlog, when work takes more than a week or has outside dependencies. Level 3, factory, adds stages 3, 6 and 7 when work runs in parallel, items repeat, or someone reviews their own work. Level 4, self-verifying, adds stages 8 and 9 when others rely on your status.

People copy the end state. Start at the lowest level your current failure needs. Before adding a stage, write the failure that calls for it in the decision log. The failures still decide, so an item falsely marked done at level 2 means adding stage 8 then. The [maturity levels](../../docs/06-adoption-and-measurement.md#maturity-levels) are an untested proposal. The stages also work outside software, for example on an office move.

## beck
Kent Beck wrote about this in 2025, in "Augmented Coding: Beyond the Vibes". He says the values in augmented coding are much like those in hand coding: "tidy code that works". What changed is who types it. In his words, "I don't type much of that code."

That is the argument of the whole method. Code review, small batches and a definition of done are old practices. Agents now do much of the work, and they produce changes faster than people can check by hand, so skipping those practices costs more than it used to. The DORA 2025 report says the same from the organisation side: "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses". Simon Willison writes that LLMs "actively reward existing top tier software engineering practices". The new skill is building those practices into the harness, meaning the files, scripts and checks the agents work inside, so they run every time without anyone having to remember.

## old
Most of the method is established practice with a new executor. Code review becomes a reviewer agent with read-only access that never sees the author's reasoning. Trunk-based development says "the branch should only last a couple of days". That becomes one git worktree per work item, a separate checkout of the repo on its own branch. The Definition of Done, the agreed test for finished work, becomes a status script that checks every done item has evidence. Retrospectives become prompt audits. You read the context file, roles and procedures against the current state and flag instructions that point at files that no longer exist.

Everything in the left column predates AI agents. Only the names on the right are new. Now that agents carry the practices out, skipping them costs more. They do not always transfer unchanged, though. In a 2026 experiment, Birgitta Böckeler found "no clearly discernable difference" between agents told to follow a TDD workflow and agents that were not. So applying an old practice to agents still needs measuring, like any other process change. The [crosswalk](../../docs/09-why-it-works.md#established-software-engineering-practice-new-executor) maps every stage to its older name.

## end
The repository has the full guide, the templates and the status script. Start with the [quick start](../../docs/01-quick-start.md). It is written for one person adopting the method on an existing project. It gets you to level 1 in the first hour and to level 2 by the end of the first week. If you are starting from nothing, or working in a team, read the variants page next.

The [README](../../README.md) maps the rest. A worked example takes one made-up work item from proposed to done and shows every artifact along the way. Next to it are the stage-by-stage reference, the work item procedure, adoption and measurement, and a page on projects outside software. The [templates](../../templates/) folder holds the files a project copies in, from the context file to the gate checklists. The [status script](../../tools/README.md) runs as `python3 tools/verify_status.py docs/backlog.md`. It exits 0 when it finds no violations, 1 when it finds some, and 2 when it cannot read or parse the file.
